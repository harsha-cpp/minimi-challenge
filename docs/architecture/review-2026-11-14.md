# Architecture review  -  14 November 2026

## Verdict and scope

Keep the modular TypeScript/Node application, Exa as the only search service, Azure model endpoint, and SQLite. The boundaries are sensible for a local, single-user application: deterministic time/context preparation, one bounded agent loop, injectable search/model ports, and a transactional evidence ledger.

The next work should strengthen the contracts between time, memory, review and persistence. The current implementation is not yet isolated for multiple users. Existing tests pass, but five targeted reproductions expose uncovered correctness behaviours.

This review covers the **current working tree**, including uncommitted/untracked implementation files, and the separate `.context/ui-preview` copy. It does not describe a hypothetical future deployment as something already built. No application code, running clock, production database, UI preview, or API keys were changed for this review. Changes are documentation and isolated review artifacts only.

## Findings, ordered by impact

### R1 · P1 · A malformed correction can discard a known rejection

**Evidence:** `src/agent/simulation.ts:147–162`, `src/agent/run.ts:214–243`.

The reviewer can return a valid `needs_revision` issue identifying hindsight, together with an invalid correction. The validator then converts the whole verdict to `unavailable`, returning no issues. `runTurn` treats that as a reviewer outage, skips correction and publishes the original draft.

**Reproduced:** a 1940 answer revealing India's eventual independence date was returned to the client even though the scripted reviewer correctly identified temporal leakage. A nonexistent citation in the suggested correction caused the rejection to be lost. The stored review status was `unavailable`.

**Recommendation:** preserve well-formed negative findings independently of correction validity. Give those findings to the existing bounded repair path. Distinguish `approved`, `corrected`, `unchecked`, and `rejected` in execution metadata and user-facing state. A genuine reviewer outage may still provide a useful, explicitly unchecked reconstruction. This does not require snapshots or an archive-access refusal.

### R2 · P1 · The viewpoint is process-global rather than conversation-scoped

**Evidence:** `src/server.ts:19`, `src/server.ts:139–148`, `src/clock.ts:20–24`, preview `src/server.ts:123–126`.

One `SystemClock` is shared by every browser using an instance. `/api/clock` changes it globally. Requests with an explicit `asOf` are pinned correctly, but an ordinary request without `asOf` inherits whichever clock another tab last selected. Ledger and session-history routes also use the shared clock rather than the calling conversation's viewpoint. The clock offset is in memory and resets on restart unless supplied through the environment.

**Reproduced:** an existing pinned 1948 turn stays pinned, but a subsequent unpinned request uses another caller's 1990 selection.

**Recommendation:** store conversation settings and make each request explicit about `mode`, `viewpointAt` and timezone. Use the real server clock only for actual receipt/creation time. Scope Ledger visibility and history requests to the same authenticated owner and declared viewpoint. Preserve the existing per-turn immutable time reading.

### R3 · P2 · Facts mentioned only in simulation answers disappear from topic recall

**Evidence:** `src/agent/run.ts:265–266`, `src/memory/store.ts:173–176`, `src/memory/store.ts:258–259`.

Factual simulations intentionally skip background enrichment and create no legacy verified statements. Their initial FTS entry therefore contains the question but not the answer, entity names or summary. Same-chat context and exact-date recall can work, while a later topic lookup misses a name found only in the answer.

**Reproduced:** after answering “Who is the president of the United States right now?” with “Barack Obama,” a later cross-chat query about Barack Obama found zero indexed matches and zero related episodes.

**Recommendation:** index answer text as an untrusted **conversation record**, with owner and temporal filters retained. Searchability does not require promoting an answer to a verified fact. Optional summaries or candidate claims should carry their review/provenance status separately.

### R4 · P2 · Time travel can reorder a reopened conversation

**Evidence:** `src/memory/store.ts:319–323`, preview `public/app.js:596–607`.

`asked_at` stores the simulated viewpoint and also determines conversation order. When a user first asks in 2026 and then travels to 1948, reopening at a viewpoint that admits both turns returns the 1948 turn first. A new real-time message can also be omitted from the “latest” history selection because an older real-time turn has a later simulated timestamp.

**Reproduced:** creation order `[1, 2]` restored as `[2, 1]` after the second turn moved to the past.

**Recommendation:** separate `created_at`/`turn_sequence` from `viewpoint_at`. Restore UI conversations in creation order; apply viewpoint eligibility independently when compiling model context. Real receipt time already exists inside execution JSON for newer records, but it is not a first-class ordering/index field.

### R5 · P2 · Answer publication precedes the durable commit; retries have no identity

**Evidence:** `src/agent/run.ts:240–255`, `src/server.ts:82–112`, `public/app.js:503–515`.

A buffered simulation answer is emitted before `saveEpisode` commits. A storage failure can therefore follow an answer the client has already received. `done` is correctly emitted after commit, but there is no client-generated turn ID or idempotency constraint to reconcile a lost completion event with a retry. The main UI also accepts clean stream EOF without checking for `done`; the preview improves that by treating missing completion as an interruption.

**Reproduced:** with an injected save failure, the event sequence included `text` followed by `error`, and the database contained no episode.

**Recommendation:** commit buffered final answers before publishing them; keep normal streamed text explicitly provisional until committed. Allocate a turn ID before generation, make retries idempotent, and provide a status/read endpoint to recover an already committed answer. Preserve `done` as the durable-completion boundary. Add heartbeat/backpressure handling if serving through a proxy or supporting slow clients.

### R6 · P1 before shared hosting · Conversation IDs are not an authorization boundary

**Evidence:** `src/server.ts:123–137`, `src/memory/recall.ts:83–139`, preview `src/server.ts:123–143`.

The ledger, sequential episode detail routes, and preview session route have no authenticated owner checks. Recall intentionally spans conversations in the one shared store. This is coherent for the current single local user, but exposing the same application to multiple users would mix their records. A UUID session name alone does not address global Ledger and episode access.

**Recommendation:** authenticate users and partition conversations, episodes, FTS queries, claims and retrieval endpoints by owner before a shared deployment. Continue allowing cross-conversation recall **within** an owner's account. Local code binds to `127.0.0.1`; this review does not claim the service is currently public.

### R7 · P2 · Search is bounded globally, but foreground model traffic is not

**Evidence:** `src/server.ts:25–29`, `src/agent/run.ts:83–85`, `src/agent/run.ts:157`, `src/search/limit.ts`, `src/llm.ts:63–73`.

The process has four active Exa slots and a queue bound, plus four per-turn lookup slots. Foreground generation and simulation review do not share a corresponding admission limit. Each incoming chat can immediately start a model request; the 120-second turn timeout bounds duration but not the number of simultaneous requests, model output tokens, or aggregate spend.

**Recommendation:** add per-owner request limits, a global model-request budget with bounded waiting, an output-token ceiling, and consistent busy/retry responses. Record model usage and per-stage timings in production, not only benchmark hooks. Keep explicit endpoint/model/provider details out of public error text.

### R8 · P2 · Background memory enrichment is bounded but not durable

**Evidence:** `src/memory/enrich.ts:98–129`, `src/agent/run.ts:254–266`.

The two-worker, 128-job queue is in process. A crash after saving an ordinary answer loses pending summaries and claims, with no replay marker. The raw exchange survives, but its FTS entry is initially limited, and a full queue drops enrichment. No graceful-drain or persistent retry mechanism is wired in the server.

**Recommendation:** insert a memory-enrichment job in a SQLite outbox transaction with the episode. Track attempts, leases and completion, and retry idempotently after restart. A separate distributed queue is not necessary at this scale. The current enrichment method deletes and recreates claim rows; a retryable worker must preserve stable claim identities once later claims refer back to them.

## What the existing design gets right

| Boundary | Implemented strength |
| --- | --- |
| Composition | `server.ts` wires explicit model, search, clock and storage dependencies. |
| Request time | `effectiveAt` is pinned once; `receivedAt` records real research time independently. |
| Research | Exa Search and Contents are the sole active web discovery/source-reading service. |
| Prompt | Trusted time instructions are separate from original user text, prior records and untrusted source passages. |
| Budgets | Search rounds, lookup count, evidence size, turn deadline and background work are bounded. |
| Retrieval | Cache has TTL/LRU bounds and single-flight sharing; cancellation is subscriber-aware. |
| Evidence | Passage observations receive stable citation numbers and content hashes; exact admitted excerpts are saved. |
| Citation handling | Server and browser share text-node exclusions through Markdown and sanitization; code and links do not become citations. |
| Database | Parameterized SQL, WAL, foreign keys, a busy timeout and atomic episode/source writes are already present. |
| Model transport | Responses mode preserves turn-local tool/reasoning items, rejects incomplete responses and requests `store: false`; Chat Completions is also supported. |
| UI preview | Separate source/dependency copy, SQLite database, process and clock; only a read-only session endpoint was added to the backend. |

Modern retrospective pages can support older historical facts. Event-date and era-knowledge interpretation remain model judgments, with review and uncertainty handling, rather than an exact historical internet reconstruction. Citation syntax and hashes establish reference integrity, not semantic truth.

## Actual components and limits

| Component | Current implementation / bound |
| --- | --- |
| Browser | Plain HTML/CSS/JS; Markdown + DOMPurify; POST response parsed as SSE |
| HTTP service | Native Node HTTP, tested here on Node v22.16.0 |
| Model roles | Main model for generation and era review; configured fast model for ordinary-turn memory extraction |
| Context | Eight fetched turns; 18,000 history characters; 12,000 recalled-memory characters |
| Research | Three search rounds; 12 valid calls; four active Exa requests process-wide; 64 queued |
| Exa output | Up to five results; 2,500 characters per provider passage |
| Evidence admission | 6,000-character ceiling per passage; 32,000 total serialized tool-output characters |
| Time budgets | 120-second turn; 20-second Exa request including retry; 10-second review; 15-second corrective generation |
| Review | At most one generation repair and a second bounded editorial review |
| Search cache | Up to 256 entries, five-minute default TTL; fresh queries bypass completed results |
| Memory jobs | Two active, up to 128 pending, in-process only |
| Stored data | Episodes, cited source observations, ordinary extracted claims, execution metadata, FTS5 rows; legacy verified-statement tables retained |

A query-specific modern article can be reused safely as research across dates, but answers must still be synthesized for the declared viewpoint and history. The current cache stores search results, not user-personalized final answers.

## Persistence, scale and deployment

One backend process and a local SQLite file remain appropriate until measured workload shows otherwise. SQLite WAL permits overlapping readers and a writer but has one writer at a time and requires same-host shared memory; it is not a shared network-filesystem database. [SQLite WAL documentation](https://www.sqlite.org/wal.html).

The current service performs synchronous database work on the Node event loop. Larger FTS scans, read-many Ledger queries and a five-second busy wait can affect other requests under load. Add pagination, owner/cutoff-aware indexed queries, latency telemetry, backups and shutdown handling before considering a database migration. Move to a shared server database when multi-instance deployment or measured write contention requires it; splitting the agent into microservices does not resolve the current correctness issues.

Preview independence covers local files and state. Both copies still use the configured Azure/Exa accounts, so upstream quotas and billing are shared. The preview is an ignored working copy, not a merged/released application revision.

## Evaluation evidence and its limits

Re-ran the existing suites during this review:

| Validation | Result |
| --- | --- |
| Main tests | 236 passed |
| Preview tests | 240 passed |
| Type-checking | Passed for both copies |
| Targeted review reproductions | Five confirmed behaviours; isolated in-memory stores and scripted model responses |

The earlier real-service benchmark reported 16/16 era scenarios, 3/3 present-date baselines, 13.8-second simulation median and 28.3-second p95, with zero Snapshot/archive requests. That was a prior single-sample, developer-selected benchmark; it was not re-run or relabeled as new accuracy evidence here. Generation, review and semantic evaluation used the same configured main model in separate requests. The judge can share model biases, and 31 matched criteria do not prove universal accuracy or source entailment.

Extend the suite with the five reproduced cases, multi-tab viewpoint changes, repeated live samples, adversarial source text, missing dates, and claim-to-passage support labels checked against reference sources. Keep synthetic protocol tests separate from live quality measurements. No CI workflow or production admission/health/backup automation was found in the reviewed application snapshot.

## Maintenance and documentation gaps

Legacy archive/corpus/checker modules and database tables remain, but `server.ts` does not compose them into chat. `runTurn` does not forward the viewpoint as a search cutoff. This is the desired live-web era-simulation path.

However, active search types still carry a legacy `asOf` meaning, `EvidenceWindow` still imports legacy eligibility code, and `.env.example` still describes historical tests as Snapshot-based. Separate legacy types/tools from the normal live research contract to prevent accidental reactivation, and update the old setup copy.

Some older diagrams implied that all final content was committed before display, or that every answer was enriched. The diagrams accompanying this review show the actual sequence, including the early publication and ordinary-turn-only enrichment conditions.

## Recommended implementation order

1. Preserve negative review findings and make quality states explicit (R1).
2. Scope viewpoint to conversations and separate real creation order from historical time (R2, R4).
3. Index simulation answer records without asserting verified truth (R3).
4. Commit/recover answers through idempotent turns (R5).
5. Add authentication/owner isolation before shared hosting, then global model admission and a durable SQLite outbox (R6–R8).
6. Promote the chosen UI from the preview through a reviewed patch, add CI, extend quality labels/repeated benchmarks, and quarantine legacy setup/types.

The next architecture should remain a modular monolith with stronger contracts. Exa remains the only search service, and no Snapshot dependency is proposed.
